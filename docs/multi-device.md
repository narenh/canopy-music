# Multi-device Canopy Music: zones

Status: built on the `tvos-spike` branch (see "Build status" at the end). Screens: [multi-device-mockups.html](multi-device-mockups.html).

## Model

- A **zone** is one queue playing in one place. Usually a home has one zone; a big house might have Upstairs and Downstairs.
- Each zone has exactly one **hub**: the iPad or Apple TV that plays the music. The hub owns the queue, the base playlist, the speakers, the settings and the guest web server.
- Every other Canopy Music device that opens the zone is a **display**.
- Phones use the web page: guests always, hosts with Host Control.

|---|---|---|---|---|---|
| Search and add | ✓ | ✓ | ✓ | ✓ | |
| Reorder | ✓ | ✓ | if *Reorder from phones* | if *Reorder from phones* | |
| Play/pause, skip, scrub | ✓ | ✓ (no scrub) | | if *Playback controls on displays* | remote play/pause if that setting is on |

- *Playback controls on displays* is a new hub setting, on by default.
- Displays have no admin at all. Long-pressing the logo (iPad), or Menu (TV), only offers **Leave**.

## Launch flow

**A zone exists only once its music has started.** On an iPad or Mac that's Start on the start screen; on an Apple TV it's the first song after a phone's "Start the music". Only then is it recorded (`ZoneRecord`), and so only then does it come back after a crash or offer Resume. Before that, an iPad's start screen is pure setup: no record, no phone server, no Bonjour announcement, no `.local` name, nothing joinable.

0. **A hub whose zone wasn't ended** (the app crashed, or the system quit it) goes straight back into its zone: the queue, the guest server, the Bonjour announcement and the `.local` name come back, so displays and phones reconnect by themselves. The music stays paused until someone presses play. An iPad comes back in the mode it was in: locked if the party screen was locked (so host mode stays behind the PIN), host mode if it was in host mode. An Apple TV comes back to its party screen, with the same Host Control key. A device that was showing someone else's zone starts at the zone list. If the zone can't come back (no Apple Music access, Spotify signed out, no network), the zone list shows it as a Resume row. Older builds recorded a zone at Create: one of theirs where music never started (`zoneStarted` false, or no key and no songs in its saved queue's party log) is ended at launch, as End does, and the device starts at the zone list with nothing to resume. A TV zone whose saved queue tvOS cleared from Caches is ended the same way.
1. **The zone list:** "Zones on this Wi‑Fi". It always shows otherwise, even with one zone or none (with none, the heading hides). There's no auto-join.
2. **Choosing a zone** opens it as a display, straight to the party screen. No PIN: a display can't do anything a guest's phone can't.
3. **Create a new zone** makes this device the hub:
   - **iPad (and Mac), the first time only** (no service has ever been chosen): setup runs. Step 1 picks the service (each card shows its state on a line under its name, as the start screen's menu says it; Spotify, if not signed in, pushes the Spotify setup page, then asks where music plays), then the phone-queueing step; step 2 names the zone (defaults to the device name) and sets an optional host PIN ("Skip" allowed). Then the start screen. Setup never comes back: installs that already have a service skip it, and a broken service (Spotify signed out, Apple Music access revoked) shows in the start screen's Music row instead.
   - **iPad, every time after that:** straight to the **start screen**, with the last name and PIN. It's host mode before Start: the Music section (the service row is a full-width dropdown: it shows the current service, and its menu offers only the other one, with that one's state on a second line: Spotify's "Not connected. Tap to sign in." or "Signed in as <name>", Apple Music's "Not connected", "Access is off" or "No subscription"; choosing Spotify when it isn't signed in opens the Spotify setup page full screen, and Spotify becomes the service only once the sign-in succeeds, backing out keeps the previous service, then it asks where music plays; Spotify chosen but signed out shows "Not connected" with a Sign in button that opens the same page; an Apple Music refusal shows in the row; under it, a "Plays on …" row that opens "Where should music play?", see "Sonos output"), a Zone section (Name, with the `.local` address it gives; PIN, digits only; the only place for either on the iPad, Settings has neither), Speakers, the base playlist and Up next. A back button returns to the zone list. Nothing is live: no record, server, announcement or `.local` name, and no Guests, Connected, Save or End.
   - **Start** makes the zone live in one step, once the music has actually started: it plays, then records the zone, starts the phone server, registers the `.local` name, announces the zone and locks to the party screen. The button shows a spinner meanwhile. With Spotify, another zone on the same account asks first (Cancel stays on the start screen, Join joins that zone as a display), and if Spotify has no reachable device the device picker opens and Start goes on once a device is chosen. If the music can't start, the start screen shows the error and nothing is live.
   - **In a live zone,** holding the logo opens host mode as before, but the Music row has no chevron and doesn't switch services (only ending the zone does), and the button says **Back to party** (it just locks). The base playlist, the zone name (the `.local` address follows) and the PIN stay editable. Picking a new base playlist here doesn't stop the party: the song playing plays on (or stays paused), guests' requests stay at the top of Up next, and the new playlist replaces only the old one's songs, taking over when the requests run out (see "Changing the base playlist" below). **End Zone** goes back to the start screen with nothing live.
   - A new zone always starts empty. If this device still has a zone (the Resume row), it asks first ("This ends Upstairs and clears its queue."), and ends it, as End does. Resume is the way back to the old one.
   - **Apple TV:** straight to **Scan to host**. The TV runs its server from here (the phone sets the zone up through it), but records nothing. The first phone to scan gets Host Control and sets the zone up on the web page, in two pages. **Set up this zone:** their own name (optional, in place of the usual name prompt), the zone name (with its `.local` address), and a **Music** bar showing Apple Music and whether the TV can play it: ready; "Allow Apple Music on the TV" (the TV hasn't asked yet: it asks as soon as this page opens); not allowed (with the tvOS path, Settings › General › Privacy & Security › Media & Apple Music); no Apple Music subscription on the TV's Apple Account; or "Couldn't reach Apple Music" (not signed in, offline, anything else; debug builds log the error in `tv.log`). The TV works this out at Create, when it becomes active again, and when the page asks (as the page opens, and every 4 s while it can't play); it goes only to hosts, in snapshots of a socket opened with the Host Control key (`/ws?key=…`, field `musicAccess`), and the page updates as it changes. **Continue** needs Apple Music ready and a zone name with a letter or digit. **Base playlist:** the search (with Back beside it) sticks to the top and the list fills the screen, then Shuffle and Start the music. Create no longer asks for Apple Music access itself (Resume still does). If another host starts the zone first, the usual name prompt shows then. Once a phone has scanned, the TV says "Continue on your phone" (nothing where the code was), and goes straight to the party screen when a playlist is picked. Until then the zone isn't announced over Bonjour, so it isn't in any device's zone list (and no guest is shown an empty zone); the web server and the host's QR link work all along. It's announced as soon as a playlist is loaded, and recorded when "Start the music" has started its first song. A zone left at Scan to host, or whose start failed, is gone after a relaunch. A TV hub has no settings screens; Menu only offers **End <zone>** (and saving the party, below). The Music bar is a full-width dropdown, as the iPad's Music row: tapping it offers the other service, Apple Music or Spotify, with its state on a second line (see "Spotify on an Apple TV" below). When Spotify is the service, the TV also checks its Apple Music access once (without asking), so the menu can say what's wrong with Apple Music, e.g. "Apple Music isn't allowed on the TV."

## Network

- **Discovery:** hubs advertise Bonjour `_canopymusic._tcp` (an iPad or Mac once its zone is live, after Start; an Apple TV once its zone has a playlist). The TXT record carries the zone name, the hub kind (ipad/tv), what's playing and the guest address, and for a Spotify zone (iPad or Apple TV) the account's fingerprint (`spotify`). Displays browse for it; the list updates live.
- **Addresses:** each hub announces a `.local` name made from its zone name ("Living Room" is `living-room.local`; `music.local` if nothing's left), then `living-room-2.local`… on a clash. A clash with the device's own name doesn't count: an Apple TV called "Living Room" is already `Living-Room.local`, so when the taken name resolves to one of this device's own addresses, the zone uses it as it is. It's handed out only once mDNS confirms it. Renaming the zone (iPad or web) announces the new name, and a web page on the old name moves to the new one, keeping the phone's ID, name and Host Control. Simulator builds use `canopytest-<zone>.local`, so tests never take real names. Every QR code points at its own hub.
- **Displays** use the same JSON API and WebSocket snapshots as the guest page, plus a few display endpoints:
  - `POST /api/display/hello`: a heartbeat, so the hub can list connected displays.
  - `POST /api/display/playback`: allowed while *Playback controls on displays* is on.
- **Up next** has 100 live songs (in snapshots: draggable, removable). Below them the same list carries on, read-only (no handle or remove, nothing can be dropped there), with the rest of the base playlist's current cycle, from `GET /api/upcoming?offset=&limit=` (compact rows, 100 at most per page). The web page and iPads (hub or display) load 50 more as the end comes into view, and fetch the rows shown again when the queue moves on, so a song simply gains its handle when it becomes live. The Apple TV shows only the rows that fit. The web page only rebuilds rows that changed, animates only rows on screen, and loads row artwork lazily.
- **Hosts on the web** get new endpoints, all requiring the host key:
  - `GET /api/host/playlists`: the hub's library. The web picker (Change base playlist, and a TV zone's first setup) filters it as you type, ignoring case and accents. Both pickers scroll as one sheet (heading, fields, search, list), so the list gets the whole screen; the search sticks to the top once the rest has scrolled off, and a fixed footer has a **Shuffle** switch (on by default) and the button (**Start the music**, or **Use this playlist**: in Change, a row selects and the button confirms; it asks first only if nothing has played yet and there are requests to clear, since mid-party the song and the requests stay). There's no shuffle in the web settings mid-party (the iPad keeps its shuffle button).
  - `GET /api/host/playlists/search?q=`: the music service's playlists, shown below the library matches while typing (as on the iPad; not for Spotify).
  - `POST /api/host/playlist`: load a base playlist (`shuffle: true` shuffles it as it loads, before anything plays, so the first song is random too). Before anything has played (a TV's setup) it starts the queue over and `play: true` starts it; mid-party the song playing plays on and the new playlist follows the requests, as on the iPad, and `play` changes nothing. Answers with how many of its songs were left out (not on the music service, e.g. iTunes Match uploads with no catalog match) and the first few titles. Snapshots carry the same (`skippedOnLoad`, `skippedTitles`) until another playlist loads: the iPad shows "3 songs aren't on Apple Music" under the base playlist (tap for the list), the web settings sheet shows it under Base playlist, and an Apple TV's host also gets it once as a toast. Debug builds' demo library has "Road trip", which leaves 4 out.
  - `POST /api/host/settings`: zone name, queue and reorder from phones, display controls, Wi‑Fi, and `crossfade` (the party page's Crossfade button; the hub keeps its own length); any subset (the web sheet saves each change as it's made). Not the iPad's unlock PIN, which is set only on the iPad.
  - `GET /api/host/details`: the Wi‑Fi details and the connected displays. The Wi‑Fi password is never in the snapshots guests get; displays' socket (`/ws?display=1`) carries the Wi‑Fi details, so they show the hub's Join Wi‑Fi code and follow changes live.
  - `POST /api/host/stop`: ends the zone (any hub), exactly as ending it on the hub does. The page asks first.
  - `POST /api/host/save-playlist`: saves the party as a playlist (`name`, `onlyRequests`). Answers `{saved: n}`, or an error with `{error: "…"}` (409 when there's nothing matching to save, 502 when the service failed). `GET /api/host/details` also carries `party`: the suggested name, how many songs would be saved either way, and where it saves.
  - `GET /api/host/invite.png`: the "Add another host" QR, rendered by the hub.
- **Host keys are kept per hub:** snapshots carry the hub's device ID (`hubID`), and the page keeps one key per hub. A hub that refuses a key only drops its own, so a phone that's a host of two zones (or of a zone whose address another hub later takes) stays a host of both. Keys move along with the phone's ID and name when the page moves to the friendly address.
- **The web page's splash:** until the page has settled on its address (the hop from the IP to the `.local` name included) and has the zone's first snapshot, it shows the "canopy music" lockup on the Dusk violet background (drawn in CSS, the same as music.canopysf.com) with "Connecting to <zone>" ("Connecting…" before the name is known), never the empty party screen. If the connection drops later, a slim "Reconnecting…" bar sits over what was showing. The lockup (`logo-music.png`) is rendered from the app's logo and Montserrat Bold to match the marketing header, since only a flattened copy of it existed. The splash's base colour (#2a1748, under the gradients) is what Safari 26 tints its status bar and toolbar with while the splash shows; once it fades, a .bar-tint pulse sets them to the page's own colour.
- **Debug builds' web log:** a debug hub answers `GET /api/debug/log?probe`, and the page then posts what it did with its splash and first screen (timestamps, the redirect, the host check, the first snapshot, the setup sheet opening, and what's on screen: the splash's and setup sheet's computed styles, the element at the top, middle and bottom, the page background, the viewport) to `Library/Caches/web.log` in the hub app's container. `GET /api/debug/log` reads it back. Release builds have neither route, and the page sends nothing.
- **If a hub disappears,** displays show "Lost connection to <zone>" and keep retrying. The queue is saved on the hub.

## Changing the base playlist

`PartySession.load(playlist:shuffled:)` is the one way in, from the iPad's host screen, the web page and the Apple TV's setup, so all three behave the same. What it does depends on whether the music has started in this session (a song actually began playing, or the queue came back from disk with one under way after a relaunch), not on the app's idea of "live":

- **Before the music has started** (the iPad's start screen, a TV's setup, or after a Start that failed): it starts over. The queue and requests are cleared and nothing plays until `play()` (Start, or the web's "Start the music"). Ending the zone makes the next load a fresh start again.
- **Once it has** (a live zone, playing or paused): nothing stops. The current song plays on, untouched, as do any song change or staging already in flight. Guests' requests move to the top of Up next, in their order, and the new playlist (shuffled first if asked) replaces only the old playlist's songs, after them. Its first cycle leaves out the song playing and the requested songs. History and the party log stay; the "songs left out" note is the new playlist's.
- **The next song:** an engine that can swap its staged song (Apple Music, demo) is restaged with Up next's new first song. A next song already handed to Spotify (locked, follow mode) can't be taken back, so it stays first and locked, whether it was a request or the old playlist's, and the requests and the new playlist follow it. If nothing was locked yet, follow mode's staging picks up the new first song as usual, 20 s before the end.
- **Never stuck:** if nothing is current but Up next has songs (the queue ran dry, then a guest added one), the party screen shows a lone Play button that starts Up next: on the hub, and on displays while *Playback controls on displays* is on.

## Spotify sign-in through the relay page

Since 2025 Spotify only accepts `https` redirect URIs (and `http://127.0.0.1`). An Apple TV has no browser, and the phone signing it in can only reach it at a plain `http` LAN address. So every sign-in, iPad, Mac or TV, goes to one static page, the relay: **`https://music.canopysf.com/spotify`** by default ([canopy-music-relay](https://github.com/narenh/canopy-music-relay); its README and `spotify.js` are the contract). Users register exactly that one Redirect URI.

- **`state`** (`SpotifyRelay`, CanopyMusicCore): compact JSON, base64url without padding, at most 512 characters: `{"v":1,"n":<nonce>,"to":"app"|"tv","host":…,"port":…}`. The nonce is 32 base64url characters, fresh per sign-in. `host` and `port` are for a TV only; port 80 is left out.
- **The relay** forwards `code` or `error`, and `state`, to `canopy-music://spotify-callback?…` (`to: "app"`) or `http://{host}[:{port}]/spotify/callback?…` (`to: "tv"`, only for a single-label `.local` name or a private IPv4 address).
- **PKCE** (`SpotifySignInRequest`): the verifier never leaves the device that started the sign-in, and Spotify's tokens come straight back to it. `redirect_uri` is the sign-in page setting, character for character, in both the authorize request and the token exchange. Refreshing doesn't use it, so changing the sign-in page keeps the current sign-in.
- **iPad and Mac:** `ASWebAuthenticationSession` with callback scheme `canopy-music`; the relay's `location.replace` to `canopy-music://spotify-callback` ends the sheet. A callback whose nonce doesn't match isn't used; `error=access_denied` (Cancel on Spotify's page) is quiet.
- **A Redirect URI that isn't registered** (missing or mistyped in the Spotify app): Spotify shows "Invalid redirect URI" on its own page, which the app can't see (the sheet only ends when the user closes it). So when the sign-in sheet is closed without an answer, the Spotify setup page says "Did Spotify say "Invalid redirect URI"? Add https://music.canopysf.com/spotify to your Spotify app's Redirect URIs.", and the start screen's Spotify row says "Add https://music.canopysf.com/spotify to your Spotify app's Redirect URIs.". A token exchange Spotify refuses over the redirect URI says it too. A failed sign-in doesn't sign out the current one.
- **The sign-in page setting** (advanced, for people hosting their own copy of the relay): Default (music.canopysf.com) or Your own. The address is checked before it's saved: `https` (a typed address without a scheme gets `https://`), loads, and carries `<meta name="canopy-music-relay" content="1">`; the result shows under the field ("Canopy Music sign-in page found.", "Use an https:// address.", "Couldn't open this page.", "This isn't a Canopy Music sign-in page.", "That isn't a web address."), and Sign in waits for a good one. It's on the Spotify setup page (iPad, Mac and the TV's phone page alike: a collapsed Advanced disclosure at the bottom, whose subtitle, readable while collapsed, says "Only for people who host their own copy of the Canopy Music sign-in relay. Most people can ignore this."; on the TV, the TV fetches the page, so the phone never needs to reach it) and in iPad Settings (a Spotify section, when Spotify is the service: Sign-in page, Default / Your own, and its page, headed with the same line). Changing it keeps the sign-in; the Redirect URI shown to register follows it.

## Spotify on an Apple TV

The TV runs the iPad's `SpotifyEngine`, `SpotifyAPI` and `SpotifyCatalog` (the `CanopyMusic/Spotify` folder is in both targets), so follow mode, the reattach after a relaunch (`attach(expecting:next:)`) and the locked staged song are the same. Its tokens are in the TV's keychain.

- **Choosing it:** the setup page's Music bar is a dropdown offering the other service (`POST /api/host/service`), only while the zone waits for setup. Spotify's option says "Not connected. Tap to sign in." or "Signed in as <name>"; signed in, choosing it switches at once. The TV swaps the service under the same `PartySession` (`replaceService`), so the phone stays connected; it's saved as `provider`, and the page's playlist picker starts over.
- **Setting it up on the phone,** on its own page of the setup sheet (Connect Spotify, with Back to the zone page): choosing Spotify while it isn't signed in opens it, as do "Sign in to Spotify" under the bar (Spotify chosen, signed out) and "Sign in again or change the Client ID" (signed in). It has the numbered steps for creating the Spotify app (the dashboard link opens in a new tab), the Redirect URI with Copy (following the sign-in page setting), the Client ID (`POST /api/host/spotify/client-id`; changing it signs the TV out), **Sign in to Spotify**, a note on family sharing through User Management, and Advanced with the sign-in page (`POST /api/host/spotify/sign-in-page`, checked on the TV). The service doesn't change while this page is open: Back leaves it as it was.
- **Sign-in** (`SpotifyHubSignIn`): the page asks the TV (`POST /api/host/spotify/sign-in`), which makes the verifier and nonce and answers with Spotify's page; the phone opens it in the same tab (what was typed on the page is kept in `sessionStorage`, with whether the sign-in left from Apple Music). `state` names the address the phone used for the TV (its `Host` header) when that's a `.local` name or private IPv4 address, else the TV's `.local` name, else its IP, so the phone comes back to the same address with its saved host key. Spotify sends the phone to the relay, the relay to `http://<tv>/spotify/callback`, and the TV checks the nonce, exchanges the code and redirects to `/`. Signed in, the page goes back to the zone page with Spotify chosen (it switches the service then, if the sign-in left from Apple Music) and shows "Signed in as <name>" and where music plays; still signed out, it opens the Spotify page again. `/spotify/callback` answers only while a sign-in is pending (10 minutes), only with its nonce (400 otherwise; the sign-in stays pending), and only once (404 after). Back from Spotify's page in the browser leaves it pending; signing in again starts over. A phone that comes back still signed out is told to check the Redirect URI.
- **Status** goes only to hosts, in snapshots of a socket opened with the Host Control key (field `spotify`, a `SpotifySetup`), as `musicAccess` does: not set up, signed out, signing in, the last error, signed in as <name>, the devices Spotify lists, the chosen one, the sign-in page, and another zone on the account. The TV reads its profile and devices when the page asks (`POST /api/host/music-check`, as it opens and every 4 s), at most every 3 s.
- **Where music plays:** after sign-in, Spotify's devices as rows under "Plays on" (`POST /api/host/spotify/device`), then the Sonos rooms (see "Sonos on an Apple TV"). The TV itself can't be the speaker: Spotify's tvOS app is only a Connect device while it's open, and Canopy Music is on screen, so the page says music plays from a speaker, phone, or computer with Spotify open. **Continue** needs the sign-in and the chosen device listed (or Sonos rooms ready).
- **Same account:** a TV announces the account fingerprint in its TXT record, as an iPad does, so iPads see a TV zone on their account, and the TV sees theirs. With another zone on the account, the page's Music bar says so, and Continue (and Start the music) asks: "Another zone is using this Spotify account. End <zone> to start a new one on this Apple TV, or join it as a display." Join (`POST /api/host/spotify/join`) shows that zone on the TV as a display and takes the phone to it. Resume on the TV's zone list and the restore at launch don't go back into a Spotify zone while another zone is on the account (the list says why).
  - **Only a zone that answers counts.** A Bonjour announcement outlives a hub that quit without a goodbye (quit from Xcode, or asleep), and an iPad once asked about a Mac zone that no longer existed until the record expired. So a matching announcement is only a candidate: `ZoneProbe` (CanopyMusicServer) asks it `GET /api/zone` at its announced address, which answers `{"hub": <hub ID>, "spotify": <fingerprint or absent>}` (only what the TXT record already says; never the Host Control key or tokens). It counts only if it answers within 2 s as the same hub, still on the account. No answer (refused, unreachable, too slow), another hub at that address, or another account (or none) means it's gone: nothing is blocked or shown, and debug builds log it (`[zones]` in the console on iPad/Mac, `tv.log` on the TV). Several candidates are asked at once, and the first that confirms is the one named. A hub from before `/api/zone` (404) counts if `/api/state` answers with its hub ID.
  - **Where:** one helper decides it everywhere: on iPad/Mac Start (its spinner shows during the check), Resume and the restore at launch (`AppModel.spotifyAccountIsFree`); on the TV, Resume on the zone list, the restore at launch, and the setup page. The page asks the TV at Continue (disabled meanwhile) and at Start the music (its spinner) with `POST /api/host/spotify/conflict` (`{"zone": <name>}`, or `{}`), and the TV probes before answering; the Music bar's line names only a zone confirmed that way, checked again each time the page polls the TV (every 4 s).
  - **Debug:** the made-up zones of `-fakeSpotifyConflict <zone>` (iPad/Mac) and `-spotifyFake conflict` (TV) have no server, so they skip the probe and count as answering.
- **The party page** for a TV Spotify zone is the iPad's: the locked next song, foreign tracks as "From Spotify", Spotify's own queue above Up next, and the player issue in the web settings.
- **Debug:** `-spotifyFake notSetUp|signedOut|signedIn|noDevice|asleep|conflict` fakes Spotify's state for the setup page without an account (the demo player plays, staged late as Spotify is); with `-autoParty`, `-fakeSpotifyFollow` and `-fakeSpotifyIssue` pose follow mode on the TV.

## Spotify zones: follow mode

Spotify's player belongs to the account, not to Canopy Music: another zone on the same account, the Spotify app, or Spotify's autoplay can change what plays. Canopy Music used to drive it (anything unexpected counted as "our song ended", so it played its next song, and the 10 s retry re-sent ours), and two controllers ping-ponged. A Spotify zone now always follows Spotify. Apple Music, demo and display behaviour is unchanged (only an engine that is a `FollowingPlaybackEngine`, i.e. `SpotifyEngine`, follows).

- **Ours or foreign** (`FollowRules.step`, CanopyMusicCore, applied to each `/me/player` poll): the track we started or advanced to is ours; reaching the URI we staged is "advanced to staged" (Canopy's queue moves on as before); anything else is foreign. A foreign track is shown, never overruled: Canopy's queue doesn't advance, nothing is played, nothing is re-sent. Back on our song, it's ours again. "Reached the end" only counts when Spotify has stopped at the end of our own song with nothing of ours queued (Spotify is idle, so Canopy plays its next song).
- **The retry:** within 10 s of a play request, our track is re-sent once only if Spotify is idle (no player state, no device, nothing loaded, or paused) or still on our previous song. An unfamiliar track playing is someone else's choice and is followed. Never after a pause since the request: a dropped engine's retry once started Spotify on the old device after the music had moved to Sonos.
- **Now Playing** (iPad, phone page, displays, Apple TV) shows what Spotify actually plays: `PartySession.nowPlaying` is `externalCurrent ?? state.current`. A foreign track has no requester; it says "From Spotify", quietly. Canopy's `current` stays underneath until Spotify reaches our next song. Foreign tracks that play go in the party log with no requester, so "Only songs guests added" leaves them out and saving everything includes them.
- **Up next, top to bottom:** Spotify's own queue items that Canopy didn't put there (`foreignUpcoming`: read-only, locked, no requester, no drag or remove); Canopy's locked next song (the one handed to Spotify), once, with its requester; then the rest of Canopy's queue, editable as before. Spotify's queue lists our staged song too: it's matched by URI and shown once, as ours, at its first place; foreign items ahead of it stay ahead. Items after it aren't shown (Spotify's queue doesn't say which are queued and which are the rest of a context, and Canopy queues its following song ahead of a context anyway). With nothing of ours in Spotify's queue, all of it is shown (up to 20). Skip goes to what Up next shows first: Spotify's next item when it has foreign ones queued (`POST /me/player/next`); otherwise as before (which also takes back a Spotify that has been following someone else).
- **Staging** (a state machine in `PartySession`, timings in `FollowTiming`):
  1. 20 s before our song ends, lock Canopy's next song and `POST /me/player/queue` it. Timed by Spotify's own position and length, and only while Spotify is on our current song's URI: right after a song change the cached position could still be the previous song's, which locked the next song at the start of a track.
  2. A stage that fails is retried twice (after 1 s, then 2 s).
  3. Right after Spotify takes it, `GET /me/player/queue` confirms it's there. If it isn't (or every try failed), it's checked again 10 s before the end. If a check can't read the queue at all, a stage Spotify answered OK counts as confirmed.
  4. Still not there at 10 s: the song below it in Up next goes first and is locked instead; the one that failed stays just below it, for the next transition. That one is staged and confirmed the same way (right after, then 5 s before the end).
  5. That fails too: staging stops for this track. It's logged (`ErrorReport`, `[follow]` debug lines), the lock is released, and `playerIssue` ("Couldn't queue the next song on Spotify") shows as a quiet line under Up next on the party screen (hub and displays), under the base playlist in host mode, and in the web zone settings. Spotify then does whatever it does next and is followed. No further automatic recovery (open question); pressing skip plays Canopy's next song. The line goes when one of our songs plays again.
  6. If our confirmed song later disappears from Spotify's queue (seen on a track change: someone cleared it, a new context), it's staged again under the same rules.
- **Requests:** `/me/player` is still polled every 3 s. `/me/player/queue` is read only when the track changes, right after staging, and for the confirmation. After a 429, polls and queue reads wait out its `Retry-After` (stages during it fail at once, so the retry/fallback rules apply).
- **Two hubs on one account** no longer fight: each sees the other's staged song as foreign and locked, and only the one whose song is playing stages. The same-account warning stays: it asks at Start (and at Resume, or the restore at launch), and nowhere else.
- **Snapshots** gain three optional fields, decoded only if present, which older pages and displays ignore: `externalCurrent` (a `QueueItem` with no requester), `foreignUpcoming` (`[QueueItem]`, omitted when empty; IDs stay the same while an item stays in Spotify's queue, and a foreign item that starts playing keeps its ID as `externalCurrent`), and `playerIssue` (a string). The version and epoch rules are unchanged.
- **Debug:** `-fakeSpotifyFollow` (with `-autoParty` and the demo service) poses a foreign track playing, two Spotify queue items and the locked next song, since the simulator can't reach Spotify; `-fakeSpotifyIssue` adds the issue line.

## Sonos output (spike, iPad, Mac and Apple TV hubs)

A zone's songs can play on Sonos rooms instead of this device (Apple Music) or a Spotify Connect device (Spotify). Canopy Music still chooses every song; Sonos streams each one from the service account linked in the Sonos app (`SonosEngine`, CanopyMusicCore: it owns the group's Sonos queue, the current song then the staged one). Discovery only reads (`SonosHousehold`, CanopyMusicServer).

- **Shared by both apps** (`SonosOutputController`, CanopyMusicServer): the chosen rooms and account (kept as `sonosOutput` and `sonosAccounts` in UserDefaults, with every account seen as `sonosKnownAccounts`; not with `-sonosFake`), making the session's `SonosEngine`, rooms joining and leaving, volumes, discovery news (`householdRefreshed`: new addresses, an account found, which rebuilds the session), and what a host's phone is told. The iPad's `AppModel` and the TV's `TVModel` only build and rebuild their sessions (`onOutputChanged`) and say when the output may move (`canChangeOutput`).
- **Linked accounts** are read off favourites, queues and what's playing at each full refresh (launch, Bonjour news), and also by the room readings the speaker lists take every few seconds: a playing song from an account the household hadn't shown reads them all again and refreshes. S2 firmware lists no linked accounts, and on a real household only the current queue (Canopy Music's own) carried a serial, so what discovery finds is gone as soon as the queue is replaced.
- **No account seen: one is assumed.** A real S2 household played a linked service's songs with any serial (`sn` 1 to 8) or none, Spotify and Apple Music alike: with one account per service the serial doesn't matter. So with no account known for the service, the rooms are selectable at once and stream with serial 1 (`SonosOutputController.assumedSerial`; never kept as the choice, never shared). An account that's known (seen, remembered or learned from another hub) always wins; it matters when a household has several for a service ("Whose account plays", which lists only known ones).
- **Remembered per household** (`SonosAccountMemory`, kept as `sonosKnownAccounts` in UserDefaults by the shared controller, so both apps): every account discovery shows, with where it was seen (a song title, the room), when it was last seen, and the zone it was learned from if another hub told it. Keyed by the Sonos household id (`Sonos_…`, DeviceProperties `GetHouseholdID`, read from the topology's player at each full refresh; every room of a household answers the same), so a hub taken to another home doesn't use them. A hub's accounts are the live ones merged with those remembered for the household it reads (before discovery has read it, the household it last read). A remembered account stays usable after the queue that showed it is gone, and after a relaunch.
- **Forgotten only when Sonos refuses it** (`SonosEngine.onAccountRejected`): the first song from the account fails, with a UPnP fault on `AddURIToQueue` (the first command carrying the service URI) or its `Play`, right after the same coordinator took `RemoveAllTracksFromQueue`, before any song from the account has played. An 800 counts only once the live layout (`GetZoneGroupState`) confirms the room leads its group; otherwise it's the usual "not the coordinator", followed as before. Nothing is retried. What's known: on the real household a service that isn't linked (Tidal) was refused with 800 on `SetAVTransportURI` by the real coordinator, then 701 on `Play`; that `AddURIToQueue` refuses it the same way is assumed, not seen. A refusal that shows only as the transport stopping isn't caught. The refused account is dropped (discovery's list, the memory, the choice); with no other account known for the service, the service counts as not linked in this household until an account is seen or the app relaunches: nothing is assumed, the rooms can't be ticked, and the note shows: "Add Apple Music in the Sonos app", then "Sonos couldn't play Apple Music. Already added? Play any Apple Music song from the Sonos app once, so Canopy Music can find it." (iPad, and the TV's setup page).
- **Hubs share what they know.** `GET /api/sonos/accounts?household=<id>` (no key; 400 without `household`, 501 on a hub without Sonos) answers that household's accounts, live and remembered: service id, serial and a song title (`label`), never a token. They aren't secrets: any queue on the household shows them. A hub with no account known for the zone's service, its household id read and rooms listed, asks the other zones it sees (`ZoneBrowser`, its own excluded) after each full refresh and at each room reading (the speaker lists, every few seconds), all at once, 2 s each (`SonosAccountExchange`); the same zones at most once a minute, a new zone at once. Answers are remembered as learned from that zone (seeing the account here later makes it this hub's own sighting); no answer adds nothing. Only hubs with a live zone serve the route (announced zones are what's listed), so a hub on its start screen or zone list, or a display, isn't asked. Not built: a hub without a zone runs no server (the iPad's start screen) or isn't announced (a TV being set up); the easy way would be a separate Bonjour record from launch, with only the address, and the route served there.
- **On an Apple TV** the output is chosen on the host's phone, at setup (see "Sonos on an Apple TV" below); the iPad's own choices are unchanged.

- **Where the output is chosen:** the start screen's Music section has a "Plays on …" row (Spotify device, this iPad and its AirPlay speakers, or "Bedroom + Move"). It opens **Where should music play?**: Spotify's Connect devices, or **This iPad** for Apple Music (AirPlay, as before, with its AirPlay button), then a **Sonos** section with the household's rooms. Rooms are multi-select; each one's second line is its model, what it's busy playing (orange; ticking it takes it over), or "Not responding" (dimmed, can't be ticked). "Whose account plays" appears there when the service has several linked accounts. The separate Speakers section is gone.
- **Moving between outputs** (this iPad or a Connect device ⇄ Sonos) happens only on the start screen, before Start or behind Back to party. It rebuilds the session: the queue carries over and a song that was playing starts again on the new output where it was, so there's a gap. The old session is shut down first: its engine pauses the old output only if it was playing this zone's music, then stops all its loops (`PlaybackEngine.shutDown`), so nothing there can start again. Unticking the last Sonos room on the start screen goes back to this device (or the Connect device).
- **Live, on Sonos:** the party screen's AirPlay button becomes **Speakers** (`hifispeaker.2.fill`, not on displays). Its panel lists the rooms with a tick each; a ticked room has its own volume slider, and with two or more an **All Speakers** slider moves the group, keeping each room's balance (GroupRenderingControl `SnapshotGroupVolume` when the drag starts, then `SetGroupVolume` on the coordinator). Ticked rooms say "Playing Canopy Music"; a room being added shows a spinner and "Joining…" until the topology has it in the group. The last ticked room can't be unticked there. Volumes, groups and what other rooms play are read when it opens and every 2 s while open, so changes made in the Sonos app show up. Slider moves are sent at most every 150 ms (the latest value) and once more on release.
- **Seamless rooms** (`SonosEngine.addRoom` / `removeRoom`, run in turn with the session's own engine calls): a room joins with `SetAVTransportURI x-rincon:{coordinator}` and plays in sync, without the song restarting. A member leaves with `BecomeCoordinatorOfStandaloneGroup`. The coordinator leaving first hands the group to the next room with `DelegateGroupCoordinationTo` (`RejoinGroup` 0); commands and polls then go to the new coordinator, whose queue position is read back (the staged song's number follows it). If the new coordinator turns out not to be on our queue, the song is put back there at the same place, with the staged song behind it (a short gap, not silence). Either way, a room that left is read once more and paused if it plays on by itself. The output (`SonosOutput`, the room IDs and target) follows every change, so a relaunch plays in the same rooms.
- **Grouping at Start, from the live layout** (`SonosGroupingPlan`): right before the first play the engine reads `GetZoneGroupState` from one of its rooms (the household's cached layout, or a target saved at an earlier launch, can be stale). A chosen room that already leads other chosen rooms keeps the lead and nothing is regrouped (the output's leader follows); otherwise the first chosen room leads, leaving any group it's a member of first. A chosen room in a group led by a room that isn't chosen is taken out of it, and that room plays on as it was. Rooms that aren't chosen but are in the leading group leave it, so the music plays only where chosen. If no room answers, it groups as last read. A play that takes the rooms back from another source does the same again.
- **Regrouped outside Canopy Music mid-party:** a coordinator that's become a member of another group answers `GetPositionInfo` with `x-rincon:{coordinator}` (seen on a real Move in a Beam's group). If that coordinator is one of our rooms (Sonos, or the Sonos app, moved the group), polls and commands follow it and its queue is taken over; if not, the room counts as taken by another source and the next play takes it back. A command refused with 800 between polls reads this at once; it isn't retried.
- **After a relaunch** (`SonosEngine.attach`, as Spotify's reattach): Sonos plays on while the app is gone. The restored session's engine reads the live layout, then from each group one of its rooms leads (the one leading the most of them first) `GetPositionInfo`, `GetMediaInfo`, `GetTransportInfo` and the queue (`Browse Q:0`), sending nothing. A group on the restored song from its queue is taken over as it is: its rooms become the output, the song is current at its queue position, playing or paused where it is, and the queue's next entry counts as staged if it's the session's next song (otherwise the session stages its own). Play, pause, seek, skip and the next song then work on it without the song starting again. A group on anything else, or a layout no room answers with, is left alone: the session stays paused, and Play takes the rooms back as at Start.
- **Same household only:** rooms come from the topology of one player (the zone's coordinator first), which lists only its household. A room the topology lists that doesn't describe itself is shown as not responding.
- **What's known and what isn't** about Sonos's behaviour: joining with `x-rincon:` and leaving with `BecomeCoordinatorOfStandaloneGroup` are what SoCo (`join`, `unjoin`) and node-sonos-http-api (`add`, `leave`/`isolate`) do. `DelegateGroupCoordinationTo(NewCoordinator, RejoinGroup)` is documented in svrooij's sonos-api-docs (AVTransport) and used by node-red-contrib-sonos-plus and homebridge-zp; Sonos's own apps keep a group playing on its remaining rooms when the coordinator leaves. No source says outright that the queue and track numbers move with the delegation, which is why the engine checks and falls back. A player left on its own is reported paused (LogicMachine forum) or stopped (openHAB); the engine pauses it if not. None of this has been tried on real speakers yet: the simulator and tests use `SonosSimulator`, an in-memory household.
- **Debug:** `-sonosFake` uses a simulated household (Bedroom Beam, Move busy with another song, Kitchen not answering; `SonosFakeHousehold`, CanopyMusicCore); nothing is sent to any device. `-sonosFakeParty 1|2` starts a live party in Bedroom (and Move) with made-up Apple Music songs; `-sonosPanel` opens the Speakers panel; `-sonosToggle Move,Bedroom` ticks or unticks rooms 5 s apart; `-showOutputPicker` opens "Where should music play?" on the start screen. `-noLocalName` (iPad and Mac, as on the TV) registers no `.local` name, so a page opened on the simulator's server from the Mac (`http://127.0.0.1/?host=…`, the key from the app's `hostControlKey` default) stays there.

### Sonos on an Apple TV

The TV runs the same `SonosOutputController` and `SonosEngine` as the iPad. Its target browses `_sonos._tcp` (and allows local networking); the local-network prompt mentions Sonos speakers.

- **Setup page, "Plays on"** (under the Music bar): for Spotify, its Connect devices as rows (signed in; the TV itself never, as before); for Apple Music, **This Apple TV** ("Use Control Center to change audio output."). Then a **Sonos** section with the household's rooms, as the iPad's: several at once, each with its model, what it's busy playing (orange) or "Not responding" (dimmed, can't be ticked); a room chosen before but not found shows "Not found on this Wi‑Fi" ("Looking…" before discovery has had time), and tapping it goes back to the TV. Choosing rooms leaves the Connect device or the TV; choosing those leaves Sonos (the device's check shows only while Sonos isn't chosen). With several linked accounts, "Whose account plays" (a picker, "Account 1, played “Ribs”"). With none known, the rooms play from an assumed one (see "Linked accounts" above). Only once Sonos has refused the service: "Add Apple Music in the Sonos app" (or Spotify), then "Sonos couldn't play Apple Music. Already added? Play any Apple Music song from the Sonos app once, so Canopy Music can find it."; the rooms can't be ticked until then. The section shows only once rooms are found (or chosen before); the subtitle then says "Music plays from your Apple TV or on Sonos speakers, chosen below." (Apple Music) or "Music plays on Sonos speakers, or on a speaker, phone, or computer with Spotify open, chosen below." (Spotify). With Sonos chosen, the Spotify bar is Ready once signed in (no Connect device needed). **Continue** needs the service ready (Apple Music access, or Spotify signed in) and a valid output: Sonos rooms of which at least one is found, with an account to stream from; or the Connect device listed; or This Apple TV.
- **Engine:** choosing rooms, This Apple TV, a Connect device or another account swaps the session's engine under the same session (`replaceService`), so the page stays connected, and only while the zone waits for setup. Once the music has started the output stays (a live zone's engine isn't replaced even if discovery finds a newer reading of the account); rooms join and leave from Speakers. A relaunch's restored session gets a `SonosEngine` from the kept rooms and account, and attaches to a group still on its song (`SonosEngine.attach`); the first play groups from the live layout.
- **The volume row** (the web party page, directly under the transport, while the session's engine is Sonos's): shown exactly where the transport is, so to hosts only (the web page never gives guests transport; the Sonos routes are host-only too, and no guest routes were added). Not shown at all when the zone doesn't play through Sonos. Left to right:
  - **Devices** (a speaker-group glyph) opens the Devices sheet: the rooms with ticks (a room joining shows a spinner and "Joining…", ticked rooms "Playing Canopy Music", others their model, what they're busy playing, or "Not responding"), and a volume slider for each ticked room. Rooms join and leave without the song restarting; the last ticked room stays: its tick is dimmed and tapping it says "The last speaker stays while the music plays."
  - **The group's volume** (All Speakers): a slider with a thumb, showing the ticked rooms' average. Dragging it snapshots the rooms' volumes (`begin`), then sets the group volume on the coordinator, keeping their balance; the rooms' sliders in Devices follow at once, and the group's follows a room's slider. Disabled until a ticked room's volume has been read.
  - **Crossfade** (a crossfade glyph), on (filled with the page's accent) or off: the hub's own crossfade setting (`POST /api/host/settings` `crossfade`), which on Sonos is Sonos's own crossfade on the group. The iPad keeps it with its Settings switch (the length stays the iPad's); the TV saves it (`crossfade` default) and applies it to every session it makes, so the button always says what the group does.
  - **Sliders** (here and in Devices) are native range inputs with a 26 px thumb and `touch-action: none`; the page follows the pointer itself (pointer capture), so a drag works from the thumb or anywhere on the track (a tap still jumps), and keyboards and VoiceOver use the input as usual. They send at most every 150 ms (the latest value) and once on release. Readings don't move a slider while it's dragged, nor for 1.5 s after release (the hub's next reading may not have the new volume yet). The old sliders had an 8 px transparent thumb and no `touch-action`: iOS Safari drags a range input only from its thumb (a touch anywhere else on the track jumps there and stops), which is the likely reason they could only be tapped (not reproduced on an iPhone: the checks here ran in a Chromium phone-sized pane).
  - **Readings:** the hub reads the rooms every 2 s while Devices is open, every 10 s while just the row shows (and when the page comes back into view); setup's page: every 4 s, with its music check. An iPad or Mac hub's page gets the same row (its output itself moves only on the start screen). Zone settings no longer have a Speakers section.
- **Plumbing:** hosts' snapshots carry `sonos` (`SonosSetup`: the service, whether discovery has searched, the rooms with their status line, state, whether they can be ticked and their volume, the chosen rooms and their name, whether there's an account, the accounts, whether the session plays through Sonos (`active`), whether the music has started there (`live`), and `ready`), as `musicAccess` and `spotify` are; never `/api/state` or guests' sockets. They also carry `crossfade` (the hub's crossfade once it has set it; `PartySession.crossfade`), for the Crossfade button. Host-only routes (403 without the key, 501 on a hub without Sonos): `POST /api/host/sonos/room` (`{id, on}`; 409 for a room that doesn't answer, no account, the last room while the music plays, or moving onto or off Sonos after setup), `/api/host/sonos/off` (back to the TV or the Connect device; setup only), `/api/host/sonos/account` (`{id}`; setup only), `/api/host/sonos/volume` (`{id, volume}` for a room; `{volume}` for the group, `{begin: true}` as its slider starts), and `/api/host/sonos/read` (answers once the rooms have been read). Between hubs, not hosts: `GET /api/sonos/accounts?household=<id>` (see "Hubs share what they know"). Choosing a Spotify Connect device (`/api/host/spotify/device`) leaves Sonos during setup.
- **Debug (TV):** `-sonosFake` uses the simulated household, with demo songs whose ids Sonos carries (`SonosFakeCatalog`: digits for Apple Music, `spotify:track:…` with `-spotifyFake`). `-noLocalName` registers no `.local` name, so a page opened on the simulator's server from the Mac (`http://127.0.0.1/?host=…`) stays there.

## Decisions taken while building (review)

- **"Resume" row:** a hub whose zone wasn't ended but didn't come back by itself (see Launch flow, or it was left to show another zone) shows it first in the list ("Resume on this iPad", "Resume on this TV"). Resume comes back locked if the iPad was locked. Ending the zone removes the row. The Apple TV has the row too, so creating over its zone has something to point back to.
- **Saving the party as a playlist:** the hub keeps a log of every song that played in the zone, in order, with who added it. Unlike Up next's history it isn't capped, it's saved with the queue (so a crash keeps it), and End clears it. A song counts as played once the player has started it: songs skipped before they played, and songs that failed to play, don't; going back to a song doesn't count it twice.
  - **What's saved:** the guests' requests are the point, played or not. At save time the hub takes the log's songs, in the order they played, then the requests still waiting (the current song if it hasn't started, then Up next, in queue order). "Only songs guests added" (on by default) keeps the songs anyone added from a phone, the hub or a display; off adds the base playlist songs that played (base songs that never played stay out). A request removed from the queue, or skipped, before it played isn't saved. Each song is saved once, however often it was requested or played.
  - **Offered as soon as someone has added a song** (the count "Only songs guests added" saves): until then the party is just the base playlist, nothing worth saving, so End is a plain confirmation everywhere (iPad alert, web dialog, TV) and the settings leave out Save as playlist.
  - **Ending** (iPad sheet, web dialog) offers "Save as playlist", on by default, with a name field that starts as the party's date ("2026-10-12 ", the day the first song played, or today) for the host to finish, and "Only songs guests added", on by default. If saving fails the zone keeps going: the host can try again or end without saving.
  - **Mid-party:** iPad Settings › Save as Playlist, and the web settings sheet's "Save as playlist" row, save the same way without ending.
  - **Apple TV:** Menu › End opens an "End <zone>?" sheet that saves the songs guests added: a name field starting as the party's date (type with the remote, dictate, or use the keyboard tvOS offers on a nearby iPhone), then **Save and End** (focused first) or **End Without Saving** (destructive, so red; white on red when focused, red on red when not); Menu cancels. Left as just the date, it's saved as the date and the zone ("2026-10-12 Attic"). "Saving playlist…" while it works; on failure "Couldn't save the playlist" with **Try Again** or **End Without Saving**. Every song (not just guests') from the web page.
  - **Where it saves:** the hub's signed-in account. Apple Music: a library playlist (Apple Music API, so the TV can too). Spotify (iPad): a private playlist; sign-ins from before this need to sign in again once, since Spotify only grants the new permission (`playlist-modify-private`) through its sign-in page. Debug builds' demo service saves to a demo library that shows up in the playlist pickers; `-failSave` makes it fail.
  - **The description** credits the people who queued from their phones and gave a name, most songs first: "Queued by Sam, Phil and 6 others · Canopy Music". The hub, displays and unnamed phones aren't credited; with nobody to credit it's just "Canopy Music". It counts the saved songs, so requests still waiting are credited too.
- **Ending a zone** (iPad, TV or web, all the same) stops the music, the guest server, the Bonjour announcement and the `.local` name, so the zone leaves every device's list at once. It clears the queue, history and base playlist and deletes the saved queue, so the next zone on that device starts empty. Settings stay: zone name, PIN, Wi‑Fi, the toggles, Host Control and its phones, and the service sign-in. An iPad or Mac goes back to its start screen (the web page's End dialog no longer says where it goes); an Apple TV to its zone list.
- **"Queue from phones" isn't offered on a TV hub,** since the web page is how a TV zone is run.
- **Displays add songs as "<zone display name>"** (e.g. "Kitchen iPad"), so the requester pill shows where a song came from. The hub keeps the display's device ID on them as a phone's client ID, so a display iPad can remove the songs it added (press and hold, **Remove from queue**), through the phones' `POST /api/remove`, which refuses anyone else's and the locked next song. Nothing else can be deleted from a display. A TV display can't add, so it has nothing to remove.
- **The device-name default needs Apple's user-assigned-device-name entitlement** on iOS 16 and later. Until it's granted, the default is "iPad" / "Apple TV".

- **TV hubs use demo songs in the simulator,** since the simulator can't play Apple Music. On a real Apple TV they use Apple Music and ask for access when the host's setup page opens. `-musicAccess ok|notDetermined|denied|noSubscription|error` (debug builds) forces what the setup page is told; with `-musicAccessAfterPrompt <status>`, a forced notDetermined turns into that 3 s after the page asks, as if the prompt had been answered.
- **The TV's zone name defaults to the Apple TV's device name.** The first host can change it on the setup page.

**Apple TV and Apple Music (found on a real Apple TV, 12 Oct 2026):**
- The TV app shares the iPad's bundle ID (`com.canopysf.CanopyMusic`). That's required for one App Store listing across iPad and Apple TV, and the separate `com.canopysf.CanopyTV` ID had no MusicKit service, so every Apple Music request failed.
- Library playlists' songs are fetched fresh from the catalog on tvOS. The catalog songs that come with library tracks can't start a fresh player there: the player connection drops and the app hangs. Verified on Living Room with two playlists.
- **A failed play no longer freezes the app.** After a failed play the session still counted the song as loaded, so it staged the next song onto the broken player, and Apple's player then blocked the main thread for 30 seconds or more (2 of 5 runs). A failed play now leaves nothing loaded. Verified on Living Room: 8 of 8 forced failures stayed responsive.
- The TV's debug-only `-playTest` screen plays Apple Music without the rest of the app, for telling Apple bugs from ours.
- **The web page's setup sheet, settings and invite modals** in a real phone browser (only the API behind them was exercised).
